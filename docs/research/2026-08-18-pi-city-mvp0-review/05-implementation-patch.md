# Pi City MVP-0 实施补丁：先验证 Agent Game，再扩写内容

## 本补丁改变什么

这不是新的宏观愿景，而是对现有游戏设计 v0.2/v0.3 的收缩与加固。它采纳外部评审的结论：下一阶段不是生产 12 个任务、完整城市、正式美术或深度 Trace 工具，而是用 3 个短任务验证一个可被推翻的核心心跳。

```text
居民请求
  → 玩家进行一次有理由的参与
  → Pi 观察 / 行动
  → 新发现回到思考塔
  → Pi 的下一步因新事实改变
  → Pi 确认是否真正办好
  → 居民与城市留下变化
```

MVP-0 必须同时证明三件事：这个心跳不是固定 SOP；玩家的参与不是跟高光点击；故事中的体验能够在未来翻面到真实 Pi Trace 的同类因果。

## 一、MVP-0 锁定范围

| 做 | 不做 |
|---|---|
| 灯塔、邮包、喷泉三个任务。 | 第四任务以后、完整第一季、城市等级和发现册。 |
| 思考塔、六地点、Pi 路线、发现物、温和绕路。 | 自由跑图、迷宫、战斗、潜行、倒计时、货币。 |
| 动态状态表：地点回访、跳过、顺序变化。 | 用固定地点序列演示 Pi。 |
| 喷泉任务的 A / B / C 核心动词对照。 | 预设“指下一站”必然正确。 |
| 一张 Story → Trace 翻面卡与兼容 Trace 接口。 | 完整 Trace Explorer 内嵌、故事自动生成真实日志。 |
| 5–8 名非技术玩家观察试玩。 | 用相近游戏评论替代 Pi City 自己的需求验证。 |

## 二、最小实现模块

| 模块 | 职责 | MVP-0 最小能力 | 关键边界 |
|---|---|---|---|
| `TutorialScenario` | 驱动三任务的故事、状态和分支。 | 根据当前事实开放行动；支持可选发现与温和绕路。 | 所有事件 `source: tutorial`，不可写入真实 Trace。 |
| `StoryState` | 保存 Pi 当前知道、携带、未确认的事实。 | `facts`、`openQuestions`、`artifacts`、`visitedPlaces`、`outcome`。 | 事实驱动地点意义，地点不驱动固定流程。 |
| `WorldCue` | 将状态变为 Pi 路线、地点、物件与城市变化。 | 思考塔回流、地点亮起／熄灭、回访与城市后果。 | 不使用“必经第 N 步”高光。 |
| `CoreVerbVariant` | 在喷泉任务切换 A / B / C 玩家权力。 | 指路、整理发现、提出确认问题。 | 三版共享故事、地点、美术与结果。 |
| `ConceptPattern` | 将教学经验映射为 Pi 的一般因果模式。 | 支持 `tool-result-reshapes-next-decision`。 | 概念不等于 Observed 事实。 |
| `TracePatternMatch` | 指向兼容真实 Trace 的最小证据窗口。 | 工具结果、Context Diff、后续决策的 3–5 事件深链。 | 不匹配就不展示真实示例。 |
| `ResearchCapture` | 为试玩保留解释性数据。 | 选择、停顿、绕路、复盘打开、主持人观察。 | 不给玩家评分，不收集敏感内容。 |

## 三、任务与变体分配

| 任务 | 它验证什么 | 玩家权力 | 动态循环必须出现什么 |
|---|---|---|---|
| 灯塔 | 行动不等于确认。 | 默认指路，但允许过早回信。 | 观察或过早回信都能启动；花园只在“尚未确认”时有意义。 |
| 邮包 | 过去信息与当前观察共同影响判断。 | 默认指路，提供先后两条可完成路线。 | 图书馆与观察台任意先后；邮局从半成功到送达。 |
| 喷泉 | 新结果回流会改变 Pi 的原判断。 | A / B / C 对照实验。 | 单一线索部分成立；两件信息回塔后，工具坊的含义和下一步改变。 |

## 四、推荐实现顺序

| 迭代 | 只验证什么 | 所需内容 | 通过后才进入 |
|---:|---|---|---|
| 0 | 玩家读得懂 Pi、地点与发现物。 | 单张低保真地图、Pi 剪影、六地点、一个发现物回流动画。 | 任务状态。 |
| 1 | 玩家理解动态循环。 | 喷泉任务的线性骨架 + 两件事实回塔 + 路线变化。 | 灯塔与邮包。 |
| 2 | 玩家不把 Pi 当固定 SOP。 | 三任务动态状态、回访／跳过／顺序变化。 | 核心动词对照。 |
| 3 | 玩家权力到底应该是什么。 | 喷泉 A / B / C 三版本，保持视觉与叙事一致。 | 翻面卡。 |
| 4 | Story 和 Pi 概念能否正确连接。 | 一张概念翻面卡；最小 TracePatternMatch 或无匹配空态。 | 试玩与决策门。 |

任何迭代若核心理解失败，回退到前一层修改；不要通过增加新地点、文本、成就或装饰来“补救”。

## 五、试玩脚本的三条硬问题

完成每个任务后，主持人只需要问一条与该任务相关的无术语问题；最终再问一条区分 Story / Trace 的问题。

| 任务 | 固定追问 | 目标回答 |
|---|---|---|
| 灯塔 | “为什么 Pi 修好灯后还没有立刻回信？” | “还要看看灯会不会再熄。” |
| 邮包 | “为什么 Pi 需要旧地址和新门牌？” | “旧地址可能变了，两个放一起才知道送哪里。” |
| 喷泉 | “为什么 Pi 后来换了一个办法？” | “带回来的新节拍和水压线索让它重新想了。” |
| 结束后 | “城市故事和真实 Pi 例子是什么关系？” | “故事是在说明一种 Pi 的行为；真实例子能让我看那种行为在实际运行里怎样发生。” |

## 六、决策门

MVP-0 不以“做完”作为通过标准。首轮试玩后的决策必须按下表执行。

| 证据结果 | 解释 | 允许的下一步 |
|---|---|---|
| H1、H2、H3 三项通过。 | 动态循环、玩家判断、结果回流成立。 | 制作高保真三任务视觉垂直切片，再验证情感与重玩。 |
| H1/H3 通过，H2 失败。 | 玩家理解 Pi，但不享受当前玩家权力。 | 选择或重做 B / C 版本；不得扩写任务。 |
| H2 通过，H1/H3 失败。 | 有选择感，但 Pi 学习映射不成立。 | 重做回流演出、状态规则与 Story→Trace 翻面。 |
| H1/H2/H3 均失败。 | 当前“城市任务”尚未成为 Agent Game。 | 暂停该入口，重新定义核心动词。 |
| H1/H2/H3 通过，H4 弱。 | Pi 学习成立，但城市尚不够有留存魅力。 | 迭代居民关系、可选发现与城市持久变化。 |
| H5 失败。 | 产品存在误教 Pi 或 Story/Trace 混淆。 | 冻结任何深度学习扩展，先修正来源边界和翻面卡。 |

## 七、下一位实现者的交接问题

实现者应在开始前确认以下问题，而不是自行把不确定处补成固定逻辑：

1. 教学关卡事件放在 `src/experience/`、`src/game/` 还是单独的 `src/tutorial/`，才能保持对 Semantic Trace 的零写入？
2. 现有 `GameSession` reducer 是否能承载 `StoryState`，还是应严格分开，避免 Predict 与教学故事彼此污染？
3. `Context Snapshot` / Diff 目前能否可靠支持 `tool-result-reshapes-next-decision` 这一 TracePatternMatch？若不能，空态要如何明确显示？
4. Pi、物件、路线和地点状态怎样在现有 Three.js World 中做成数据驱动 cue，而不把任务故事写死在组件里？
5. A / B / C 版本怎样通过 scenario config 切换，确保唯一差异是玩家权力？

这些不是可在美术阶段忽略的工程细节；它们决定 Pi City 是否能在保持 evidence-honest 的同时拥有真正的游戏入口。
