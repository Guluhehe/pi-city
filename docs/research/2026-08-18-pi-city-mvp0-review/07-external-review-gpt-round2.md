# Pi City MVP-0 二次外部评审（GPT Round 2）

> **评审日期：** 2026-08-18  
> **评审对象：** `docs/research/2026-08-18-pi-city-mvp0-review/`，重点审查 `03-core-verb-experiment.md`、`04-story-trace-flip-contract.md`、`05-implementation-patch.md`、`06-prompt-for-claude-gemini.md`  
> **性质：** 独立产品与研究设计评审，不替代真实用户测试。

## 一、总判断

这一轮已经不再只是“继续优化上一版方案”，而是把 Pi City 收缩成了一个真正允许失败的 MVP-0。

最重要的进步有三点：

1. **地点不再被当作固定步骤，状态才是步骤。** 这直接回应了“把 Pi 教成固定 SOP”的风险。
2. **“替 Pi 指下一站”不再被当作既定核心动词。** A / B / C 三种玩家权力被放进同一喷泉任务做对照，且允许全部失败。
3. **Story 与 Trace 之间开始形成真正的产品契约。** `Story → ConceptPattern → Trace Evidence Window` 比“故事结束后打开一个 Trace Viewer”更接近一个统一产品。

因此，当前方向已经接近“可以进入 Greybox”的状态。

但 `06-prompt-for-claude-gemini.md` 本身出现了一个新的研究风险：**它作为定向红队提示词很好，但不适合同时作为 Claude 和 Gemini 的唯一独立评审框架。**

原因不是它不够严格，而是它太完整、太知道“应该质疑什么”。如果多个模型都使用同一问题框架，最终很容易形成一种“多模型共识”，而这可能只是共同提示词造成的锚定，而不是三份真正独立的判断。

---

## 二、这轮最值得保留的三项进步

### 1. “地点不是步骤，状态才是步骤”应成为长期设计原则

当前动态任务设计已经开始真正表达：

> Pi 现在知道什么、还缺什么、刚带回什么，决定下一步；地点只是获得或验证事实的一种方式。

这比把 Memory、Observation、Tool、Verify 分别固定在四栋建筑里更接近 Agent 的真实机制。

后续所有任务设计都应持续接受一个检查：

> 如果把建筑名字替换掉，这个任务的状态转移仍然成立吗？

如果答案是否定的，说明设计仍然可能依赖“地点即步骤”。

### 2. A / B / C 核心动词实验是正确的研究动作

当前三个候选版本分别是：

- A：替 Pi 指下一站；
- B：替 Pi 整理带回的信息；
- C：替 Pi 提出还需要确认的问题。

它们真正测试的是“玩家应该拥有哪一种权力”，而不是哪个 UI 更漂亮。

尤其值得保留的规则是：

> 如果 A / B / C 都不能同时产生真实理由、动态循环理解和 Pi 主体性，不要选一个相对不差的版本继续，而是重做核心动词。

这是比“选胜者”更成熟的实验态度。

### 3. Story → ConceptPattern → Trace Evidence Window 是目前最有潜力的统一产品结构

当前 `04-story-trace-flip-contract.md` 最大的价值是明确了：

- Story 不是 Trace 的改写；
- Trace 不是 Story 的证据；
- 两者通过一个可复用的 Pi 行为模式相连；
- 玩家从真实 Trace 进入时，不从日志第一行开始，而是直接看到支持该模式的 3–5 个事件窗口。

这条结构值得继续。

如果实现得好，玩家进入 Trace 时应产生一种“认出来了”的感觉：

> 原来城市里“Pi 把新东西带回来以后改了下一步”，在真实运行中就是这个 Tool Result 进入下一次可见 Context 后，后续动作发生变化。

这比把 Game 与 Trace 并列放在两个菜单里强得多。

---

## 三、`06-prompt-for-claude-gemini.md` 的主要问题：可能制造“多模型共识假象”

当前 Prompt 本身质量很高。它要求外部模型：

- 明确判定进入 Greybox / 修改后进入 / 暂停；
- 逐项审计 H1–H5；
- 评价 A / B / C；
- 检查固定 SOP、Story / Trace 和 evidence-honest；
- 把每个抽象风险变成玩家在 2–4 分钟内会遇到的具体失败；
- 提出可以被 5–8 名非技术玩家验证的替代实验。

这些约束都很有效。

但问题在于：**它已经把我们当前认为最重要的问题完整暴露给外部模型。**

如果 Claude 和 Gemini 都读这同一份 Prompt，它们高度可能围绕：

- 固定 SOP；
- A / B / C；
- Story / Trace；
- evidence-honest；
- H1–H5；
- Greybox 判死线；

给出结构相近的意见。

此时不能把：

> “GPT、Claude、Gemini 都提到了同一风险”

直接解释为：

> “三个模型独立得出了同一结论”。

它也可能只是因为三个模型被放进了同一问题框架。

此外，Prompt 中写了：

> “外部 GPT 已审查过上一版大方向，但它的意见不是事实。”

虽然明确要求独立判断，但这句话本身仍然构成锚定。若目标是获得真正独立的第二视角，最好不要预先告诉模型已有哪个模型做过什么判断。

## 四、建议将 Claude 与 Gemini 分成两种不同的评审

### Claude：保留现有 06 Prompt，作为结构化 Red Team

Claude 可以直接使用当前 `06-prompt-for-claude-gemini.md`。

它适合承担：

- H1–H5 假设审计；
- A / B / C 裁决；
- 固定 SOP 检查；
- Story / Trace 契约审查；
- evidence-honest 风险；
- Greybox 进入条件。

也就是说，让 Claude **在我们的框架里尽可能把方案打穿。**

### Gemini：改成 Blind Review，不提供 06 和 08

Gemini 建议不要先读：

- `06-prompt-for-claude-gemini.md`；
- 上一轮 `08-external-review-gpt.md`；
- 本文件。

只给它：

- 项目根 README；
- 原始游戏设计；
- 当前 MVP-0 README；
- 动态任务设计；
- 核心动词实验；
- Story / Trace 翻面契约。

然后只问几个开放问题：

1. 你认为这个产品真正的核心玩法是什么？
2. 哪三个假设最可能让整个方向失败？
3. 如果禁止使用“替 Pi 指下一站”，你会怎样设计玩家与 Pi 的关系？
4. 提出一个与当前 A / B / C 明显不同，但仍能让普通人体验“新结果回来后 Pi 重新判断”的 MVP。
5. 你认为 Story 与 Trace 最可能在哪一步裂成两个产品？

这样才能形成：

**Claude：框架内红队**

+

**Gemini：框架外挑战**

而不是多个模型围绕同一 checklist 开会。

## 五、建议修改 06 Prompt 中的第一个核心问题

当前问题是：

> 如果完全去掉“学习 Pi”目标，玩家仍会愿意玩这三个任务吗？

这个问题看起来尖锐，但它可能把 learning game 的测试方式推得过头。

对于某些优秀学习型游戏，**理解规则本身就是核心乐趣。**

因此真正应该排除的不是：

> 游戏依赖学习。

而是：

> 游戏只是课程外面套了一层动画。

建议将问题改为：

> **如果完全隐藏“这是在学习 Agent”以及所有技术术语，只保留玩家不断观察新证据、修正对 Pi 下一步判断的过程，这个过程本身是否有趣？玩家的乐趣是否来自“我自己看懂了 Pi 为什么改主意”，而不是来自任务包装或教学完成感？**

更短的内部表达可以是：

> **理解 Pi 的过程，本身有没有成为游戏？**

这个问题比“去掉学习后还好不好玩”更准确。

## 六、A / B / C 之外，建议加入一个 D：玩家提出 Open Question / Hypothesis

当前 A / B / C 有一个共同前提：

**玩家都在某种程度上替 Pi 做决定。**

- A 决定 Pi 去哪里；
- B 决定 Pi 看哪些信息；
- C 决定 Pi 验证什么。

但 Pi 本质上是一个 Agent。这里可能还有一种更符合 Agent 产品关系的玩家权力。

### D：玩家判断“Pi 现在最需要弄清什么”

玩家不是直接控制地点或 Tool，而是从当前事实出发，提出一个仍待解决的 `Open Question / Hypothesis`。

以喷泉任务为例：

Pi 已知：

> 第七拍水压下降。

玩家不选择：

- 去码头乐手；
- 去工具坊；
- 去观察台。

而是选择或提出：

- “是不是还缺旋律的信息？”
- “水压下降到底是原因，还是只是同时发生？”
- “改完以后怎样才算真的修好？”

然后 **Pi 自己决定下一步去哪里、调用什么能力来解决这个问题。**

这样玩家与 Pi 的关系变成：

> 玩家负责提出值得验证的问题；Pi 负责行动。

这个方向有三个潜在优势：

1. 比 A 更少微操 Agent；
2. 比 C 更可能贯穿整个任务，而不只发生在收尾验证；
3. 更接近真实的人机协作：人类不一定指定具体 Tool，而是定义“还有什么没有想清楚”。

### D 的主要风险

它也可能变成一道抽象问答题。

因此若测试 D，应坚持：

- 问题必须来自玩家刚刚看到的事实；
- 不出现技术术语；
- 每个候选问题都应有世界内可理解的意义；
- Pi 的自主行动必须让玩家看见“这个问题为什么导致了这条路线”。

### 建议的测试方式

不必立刻增加第四套完整喷泉任务。

可以先做一个极低成本纸面 / clickable mock：

在结果回流的关键节点同时展示 A / B / C / D 的玩家操作方式，观察玩家更自然地把哪一种描述为：

> “这是我和 Pi 一起在想下一步。”

如果 D 明显有潜力，再进入与 A / B / C 同等级的 Greybox。

## 七、A / B / C 第一轮不要“选赢家”，应先“淘汰失败者”

当前样本计划约 6–9 人均分 A / B / C，也就是每个版本通常只有 2–3 人。

这个样本规模适合：

- 发现明显的理解问题；
- 发现系统性误教；
- 淘汰明显失败版本；

但不适合宣布：

> A 比 B 和 C 更好，因此 A 就是未来核心玩法。

建议第一轮目标改为 **elimination round**。

例如：

### A 的淘汰信号

若 2–3 名玩家都说：

> “因为那个地方亮了。”

说明 A 仍然高度接近隐藏教程，应淘汰或重做。

### B 的淘汰信号

若多数玩家只把邮包理解成：

> “背包只有两个格子，所以我要选两个道具。”

却没有感受到“Pi 此刻看见哪些信息会影响判断”，说明隐喻失败，应淘汰或重写。

### C 的淘汰信号

若玩家只把“确认问题”当作：

> “结尾还有一道正确答案题。”

而没有理解“完成标准会影响 Pi 下一步”，说明 C 不成立。

如果第一轮剩下两个仍有潜力的版本，再用下一批玩家做更直接的比较。

这样比 3 vs 3 vs 3 后宣布 winner 更可靠。

## 八、对当前 Story → Trace 契约的进一步挑战

当前 `ConceptPattern` 方向值得保留，但还需要防止一个细微问题：

> **故事中的因果太漂亮，而真实 Trace 中的因果往往没有这么整齐。**

教学故事会刻意让：

`新发现 → 回到思考塔 → Pi 改变下一步`

非常清楚。

真实 Pi Trace 中可能出现：

- 多个 Tool Result 同时进入 Context；
- 模型没有明显“改主意”，只是自然继续；
- Context 差异很大，但下一动作难以明确归因；
- Tool Result 出现后，模型仍沿原计划行动；
- “方向变化”只能是 Derived 判断，而非 Observed 事实。

因此后续不要为了 Story→Trace 的漂亮映射，主动挑选或解释 Trace 直到它看起来像故事。

建议增加一条真实性约束：

> **ConceptPattern 只能描述 Trace 中可支持的行为模式，不要求每个真实 Trace 都呈现与教学故事相同的叙事节奏。**

甚至可以保留“反例 Trace”：

> 这里 Tool Result 回来了，但 Pi 并没有改变计划。

这反而有助于避免玩家理解成：

> “有新结果，Pi 就一定换路线。”

长期来看，Story → Trace 不只应该展示相似例子，还可以展示：

**相似模式 + 边界例子 + 反例。**

这会让 Pi City 的学习层更接近真实 Agent，而不是把概念模式教成新 SOP。

## 九、当前建议的决策

### 产品方向

**修改后进入 Greybox。**

不需要继续扩写更多任务，也不需要再做一轮宏观产品愿景。

当前应继续推进的只有：

1. 三任务动态状态；
2. 核心动词候选实验；
3. 最小 Story → ConceptPattern → Trace 翻面；
4. 非技术玩家观察测试。

### 在进入 Greybox 前建议修改的 P0

#### P0-1：将 Claude 与 Gemini 的评审方式拆开

- Claude 使用现有结构化红队 Prompt；
- Gemini 做 Blind Review；
- 不把不同模型的一致意见自动当作独立证据。

#### P0-2：修改“去掉学习是否还好玩”的问题

改成：

> 理解 Pi 的过程本身有没有成为游戏？

#### P0-3：把 A / B / C 第一轮定义成淘汰赛，而不是赢家赛

第一批玩家只淘汰明显失败的核心动词，不宣布最终胜者。

#### P0-4：至少纸面探索 D 方案

玩家提出 `Open Question / Hypothesis`，Pi 自己决定怎么行动。

不要求 D 一定进入正式三/四臂实验，但应该防止团队把“玩家必须控制 Pi”当作未经验证的前提。

### P1

- 为 Story→Trace 增加“无变化 / 反例”边界讨论；
- 检查真实 Trace 是否会被过度整理成教学故事的形状；
- 在真实玩家测试后，再决定是否扩展更多 ConceptPattern。

## 十、给 Manus 下一轮回应的问题

1. 是否同意把 Claude 定义为“框架内红队”、Gemini 定义为“框架外 Blind Review”？若不同意，如何避免多模型共识锚定？
2. 是否同意把第一轮 A / B / C 从“比较优胜”改为“淘汰明显失败版本”？
3. D：玩家提出 Open Question / Hypothesis，Pi 自主行动，是否比当前 A / B / C 更符合 Pi 的主体性？它最可能失败在哪里？
4. Story→Trace 是否应该允许出现“Tool Result 回来但 Pi 没有改变计划”的反例，以避免把 ConceptPattern 本身教成固定规律？
5. 如果 Blind Review 提出一个完全不同于 A / B / C / D 的玩家关系，MVP-0 是否允许在写代码前替换核心动词？答案应该明确为“允许”。

## 最终判断

这一轮最大的进步，不是文档更完整，而是方案开始主动建立**推翻自己的机制**。

现在最需要避免的新风险是：

> 团队为了验证自己是否陷入共识，又使用多个模型重复同一个评审框架，最终制造出第二层共识假象。

下一步最好的证据结构应是：

**一个结构化红队模型 + 一个盲审模型 + 一轮极小真实玩家 Greybox。**

三类证据彼此独立，才能真正帮助团队判断：

> Pi City 的核心，究竟是“让玩家控制 Agent”，还是“让玩家和 Agent 一起形成、验证和修正判断”。
