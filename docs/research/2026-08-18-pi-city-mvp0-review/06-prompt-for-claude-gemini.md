## 可直接复制的提示

你是一位**独立游戏设计总监、学习体验设计师与 AI 产品评审者**。请对 Pi City 的 MVP-0 提案做一次严格、可证伪的二次评审。你的职责不是润色文档、复述方案或为了鼓励而给出泛泛好评；你的职责是判断这是否值得进入三任务 Greybox，以及它会在哪些地方欺骗团队“看起来像游戏，实际只是交互式演示”。

### 产品背景

Pi City 原本是一个将 Pi AI Agent 运行过程可视化为港口城市的产品。当前团队尝试增加一个面向非技术用户的“城市故事”入口：玩家陪小助手 Pi 帮居民办事，在观察、行动、带回新结果、重新判断、确认、回信的循环中，直觉理解 Pi 如何工作；好奇者随后可以翻面进入真实、脱敏 Pi Trace 的证据界面。

该产品有一个不可妥协原则：**evidence-honest**。教学故事是作者定义的示例，不能被伪装为真实 Agent 运行；真实 Trace 必须持续区分 Observed、Derived 与 Synthetic。

### 你必须重点回答的七个问题

1. **核心乐趣在哪里？** 如果完全去掉“学习 Pi”目标，玩家仍会愿意玩这三个任务吗？如果会，具体乐趣是什么；如果不会，为什么？
2. **核心动词成立吗？** “替 Pi 指下一站”“替 Pi 整理带回的信息”“替 Pi 提出确认问题”三种玩家权力，哪一种最可能产生真实的参与感与正确的 Pi 心智模型？是否存在更好的第四种动词？
3. **是否误教 Pi？** 动态任务状态是否足以防止玩家学成“Pi 必定按图书馆→观察台→工具坊→花园的固定 SOP”？请指出具体会误教的界面、文案或任务结构。
4. **选择是否真实？** 哪些选择只是在换台词、假分支或隐藏教程？每一个被批评的选择都请提出一种仍然低门槛、但后果更可读的替代。
5. **Story 与 Trace 是否属于同一产品？** `ConceptPattern` 与翻面卡是否足以建立“故事先体验、真实 Trace 再认出同一种因果”的闭环？哪里仍然像两个被硬拼在一起的产品？
6. **灰盒范围是否正确？** 哪些内容应继续冻结，哪些最小元素反而缺失？不要建议用更多地点、任务、收集物、迷宫、战斗、倒计时、货币或大规模美术来掩盖核心问题。
7. **如何作出决策？** 给出明确的“进入 Greybox / 修改后再进入 / 暂停并重做核心动词”结论，并说明哪 3 条玩家证据会让你改变结论。

### 严格的输出格式

请使用以下结构，用中文回答。每条核心判断都需引用相应文件名与章节标题。

1. **三句话总判断。** 明确给出进入、修改后进入，或暂停的建议。
2. **假设审计表。** 对 H1–H5 分别标记：`可信但未验证`、`设计不足`、`误教风险` 或 `应删除`，并写明理由。
3. **最致命的三项风险。** 每项写出一个玩家在 2–4 分钟内会遇到的具体失败场景，而非抽象原则。
4. **核心动词裁决。** 评价 A/B/C，必要时提出第四种动词；说明如何用现有三任务范围测试它。
5. **动态循环与真实性审查。** 指出固定 SOP 风险、Story/Trace 断裂风险与 evidence-honest 风险各至少一处，并给出最小修正。
6. **MVP-0 改动清单。** 只列出在进入 Greybox 前必须新增、删去或重写的内容，按 `P0 / P1` 排序。
7. **试玩决策门。** 给出你认为最少的 3 个通过条件，以及任一失败时团队该怎么做。

### 约束

- 不要复述文档。
- 不要只说“多做用户测试”或“提高美术品质”；请说明测试什么、什么证据意味着失败、该重写什么。
- 不要把外部相近游戏评论当作 Pi City 的需求证明。
- 不要建议将故事事件写回真实 Trace，或模糊教学故事与真实运行的边界。
- 不要用增加复杂系统来回避“核心动词是否好玩”的问题。
- 若你认为信息不足，请在结尾最多提出 3 个具体问题；不要因此回避给出暂定判断。
