# Pi City 第二章“记忆风”开场：直接优化实施记录与 GPT Review Pack

> **记录日期：** 2026-08-19  
> **评审对象：** `Pi City` 当前 `main` 分支，重点为第二章第一个任务“风筝回来了”的港口开场。  
> **目的：** 让外部 GPT 独立审查这一轮“直接改造当前场景”的实施是否真的让 Pi 更像一个可信、可协作的助理，而不只是让港口更暗、更漂亮。  
> **范围边界：** 本文记录的是已实现代码、可复核截图与当前程序化角色的局限；它不是正式 GLB 角色/环境资产的交付证明。

## 一、这轮为什么必须直接改造场景

此前项目已完成第二章资产合同、环境生产规范和视觉诊断，但用户指出一个关键问题：如果当前运行中的画面没有变得更好，继续写设计文档不会证明方案有效。因此本轮将工作重心从“等待正式资产”转为“先用现有 Three.js 几何、灯光、相机和 UI 直接改善真实可玩的港口”。

这一选择不替代正式美术生产。它的作用是尽早验证三个问题：第一，玩家是否能先读到 Pi 的意图；第二，世界中的异常、目的地和行动邀请是否形成连贯因果；第三，未来替换 Pi GLB 与环境 GLB 时，现有玩法状态机、相机语义和任务契约能否保持不变。

## 二、起点：问题不是“暗得不够”，而是叙事优先级错误

稳定基线画面使用较高曝光的广场视图。喷泉、红色环形异常和场景大体量几何占据视觉中心；Pi 位于画面下方，轮廓容易被喷泉边缘、纸页与港口前景遮挡。即使 Pi 已携带提包，玩家也很难在第一眼把它读成“Pi 正在调查、会带回发现”的信息。

> **本轮判断：** 若第一眼先读到的是“港口里有一个漂亮但抽象的装置”，而不是“Pi 注意到了一件事”，则 Pi City 仍像动态展示页，尚未成为由角色行动驱动的游戏开场。

## 五、实拍核验结论

本轮对 2560 × 720 的前后对比图进行了从左到右的五个重叠切片检查，并重新捕捉了开场、邀请、探索三阶段。结论是：第二章的冷暖层级、深度和目的地可读性已优于基线；Pi 的帽灯、主体轮廓、提包、锁扣和携带纸页也已经从暗色环境中分离。

关键改进不在于提包变大，而是它在 Pi 转向后会换到镜头可见侧。因此邀请出现时，玩家仍能同时读到“Pi 看见了什么”“Pi 随身带着什么”以及“玩家可以和 Pi 一起做什么”。完整核验已通过：**69 项测试通过、TypeScript 通过、生产构建通过**。

## 七、推荐的全章节适配原则

应将第二章验证出的实现拆为五个可复用层，而不是为每章单独复制一份 `if (missionTheme === ...)`。

1. **镜头节拍层。** 每个任务均应声明建立角色意图、展示异常/委托、交给玩家三拍镜头。镜头必须属于任务状态，不属于页面装饰。
2. **Pi 表演层。** 将 `idle-observe`、`take-note`、`turn-and-trot` 扩展为统一动作状态；每种状态同时驱动身体朝向、头灯、携带物、微光与落点，而不是只切换一段动画。
3. **携带物层。** 每章都有可被玩家看见的“Pi 带着什么回来”。携带物必须表达新信息或验证结果，不能仅是奖励图标。
4. **主题环境层。** 每章分别提供天空、路面、实用光、气候效果、前中远景锚点和一组状态化地标。章节差异应该来自世界状态，而不仅是标题、色调或任务文案。
5. **交互时机层。** CTA 必须出现在 Pi 的意图已经被表演清楚之后。玩家负责提出、判断或确认问题；Pi 自主选择路线和行动方式。

## 九、可直接复制给 GPT 的独立 Review Prompt

```text
你是一名独立的游戏创意总监、交互叙事设计师和实时 3D 体验审查者。请审查 Pi City 当前 main 分支中第二章“记忆风”的开场改造。

Pi City 的目标不是把 AI Agent 日志做成仪表盘，而是让非技术玩家在一个轻量港口冒险中理解：玩家提出值得弄清的问题，Pi 自主行动，带回发现，并会因新信息重新判断。教程故事必须 evidence-honest：它们是明确标注的作者构造故事，不可伪装为真实运行 Trace。

请先阅读：
1. docs/research/2026-08-18-pi-city-mvp0-review/29-memory-wind-opening-implementation-record-and-gpt-review.md
2. docs/research/2026-08-18-pi-city-mvp0-review/28-memory-wind-opening-visual-audit.md
3. 29-review-assets/ 下的四张图
4. src/world/FountainStoryScene.tsx
5. src/product/CityStoryHub.tsx 与 src/city-hub.css
6. src/world/memory-wind-scene-contract.ts

请不要默认接受本文结论，也不要把“灯光更漂亮”当作成功。请独立回答：

A. **第一眼可读性。** 一个完全不了解 Pi、也不知道项目背景的玩家，是否会在 3 秒内读到“Pi 注意到了异常”而不是“港口有一个抽象装置”？请指出具体画面证据。

B. **Pi 的主体性与提包。** 当前的帽灯、轮廓、提包、携带纸页和转向动作，是否真的像一个正在调查的助理？它们是否仍然像被环境道具淹没的装饰？请明确指出最强和最弱的一项。

C. **交互因果。** 从 `notice` 到 `invite` 的 CTA 是否建立在玩家已经看懂 Pi 意图之后？“和 Pi 一起看看”是否表达了合适的人机分工，还是仍然只是普通任务按钮？

D. **从第二章扩展到四章。** 本文提出的五层适配原则是否足以避免每章都变成独立的演示页面？请给出你认为必须在代码架构中补充、拆分或禁止的一项规则。

E. **正式资产接入。** 现有场景契约是否真的允许替换 Pi GLB、携带物和环境 GLB 而不重写玩法与相机？请指出最可能在资产接入时失效的坐标、尺度、动画或状态接口。

F. **严格决策。** 在以下三项中只能优先投入一项，你选哪一项，为什么：
   1) 正式 Pi GLB 与三段骨骼动画；
   2) 第二章环境材质/建筑 GLB；
   3) 5–8 名非技术玩家的无讲解可用性测试。

请以“保留 / 修改后继续 / 暂停并重做”作总判定，并输出：
- 三条必须保留的实现；
- 三条最高风险或误导；
- 三项按影响力排序、可在一周内实施的改动；
- 一项与本文路线明显不同、但可能更好的替代方案。
```

## 十、审查约束

这是一份**外部独立评审**，不是让 GPT 确认既有方向。评审意见应优先指出玩家会误读什么、何时会失去 Pi 的主体性、以及正式资产替换将如何破坏当前体验。若 GPT 认定需要暂停进一步美术生产或改写开场逻辑，应明确说明原因和最小验证实验。

同时，不应把多个模型意见相似自动当作独立证据；若后续邀请其他模型，建议至少保留一份不先阅读本 Review Prompt 的盲审，以降低同一问题框架造成的锚定。
