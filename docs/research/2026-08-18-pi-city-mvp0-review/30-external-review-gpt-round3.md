# Pi City 外部评审 Round 3：0c4ad7e 后的垂直切片裁决

> **评审日期：** 2026-08-19  
> **评审对象：** `0c4ad7e5543b8ed186ffa68b5d03c63dc43cfaf4` 及其前序第二章“记忆风”实现链路  
> **结论类型：** 修改后继续当前垂直切片；不批准扩展到全章节，也不视为 MVP-0 核心玩法已通过。

## 一、结论先行

这轮实现取得了实质进展，但进展主要发生在 **Visual Agency Layer**：

> Pi 从场景中的功能标记，开始变成一个会先注意到异常、形成意图、再邀请玩家一起判断的角色。

这值得继续。

但当前仍没有真人证据证明另外两层已经成立：

1. **Gameplay Causality**：玩家的判断与新发现是否真的改变 Pi 的下一步，而不是跟随提示和高光。
2. **Story ↔ Trace Causality**：故事中形成的因果直觉，是否能在真实 Pi Trace 中再次被玩家识别。

因此 Round 3 的裁决是：

> **继续“记忆风”垂直切片，但立即重新收紧验证范围；不得因为 Opening 变好就推广到 12 个任务或全面美术生产。**

---

## 二、这轮做对了什么

### 1. 失败原型被及时回滚，而且复盘方向正确

中间的程序化“记忆风街角”失败后，团队没有继续通过 Bloom、雾、曝光和更多灯光掩盖低模与材质问题，而是明确承认：

- 基础盒体 + 纯色材质无法证明最终电影化品质；
- 低曝光会放大资产缺陷，而不是制造质感；
- Pi、近景建筑、材质和角色动画需要真正的英雄资产策略。

这次回滚是健康的产品/美术决策。

但原失败复盘中“未获得正式资产就不要再修改实时场景”的规则写得过于绝对。后续实践已经证明：现有程序化 Proxy 仍然可以有效验证构图、镜头、角色意图和交互时机。

因此正确规则应修正为：

> **程序化 Proxy 可以验证交互与演出结构，但不得被用来证明最终美术品质。**

### 2. 开场终于开始以 Pi 的意图为中心，而不是以港口系统为中心

当前第二章开场采用：

`notice → invite → explore`

方向上是正确的。

Opening 不再一上来展示完整任务卡、信任图和城市 UI，而是先给 Pi、异常与角色视线，让玩家先看到“Pi 在注意什么”，再出现“和 Pi 一起看看”。

这比过去“系统先说任务是什么、Pi 只是地图中的一个标记”更接近 D 路线：

> 玩家不是微操 Pi 的路线和工具；Pi 先形成可读意图，玩家再参与值得弄清的问题。

### 3. 场景契约开始具备可扩展性

`memory-wind-scene-contract.ts` 将：

- Anchor
- Shot
- Asset State
- Mission Phase

分离出来，方向是合理的。

`pi-start`、`pi-return`、`memory-wind`、`red-door` 等锚点，以及 arrival / notice / choice / departure / return / complete 的镜头意图，都可以在未来正式 GLB 替换时继续保留。

这一层应该继续作为正式美术和任务语义之间的边界，而不是未来重新把坐标、动画和任务逻辑塞回组件条件判断中。

---

## 三、当前最重要的新风险：验证范围正在膨胀

从上一轮外部 Review 到 `0c4ad7e`，仓库已经快速扩展出：

- 四个 Chapter；
- 12 个任务；
- 城市信任图；
- 发现册；
- 第二章完整资产生产包；
- 多组美术生产规范；
- Chapter 2–4 扩展合同；
- 大量截图、审计和生产文档。

这些内容本身不一定错误。

问题是：

> **最关键的 MVP-0 玩家证据还没有拿到，下游生产已经明显提前。**

此前自己的 `14-goal-alignment-gap-audit` 已经准确指出当前 P0 并不是“材质还不够好”，而是：

- 玩家为什么这么选；
- 发现带回来以后为什么改变下一步；
- 绕路是否真的有世界内意义；
- 居民是否真的记住帮助；
- Story → Trace 是否形成闭环。

这些问题并没有因为第二章 Opening 变漂亮而自动解决。

因此下一阶段必须再次恢复 MVP-0 的生产纪律：

> **真人验证以前，不再以新增 Chapter、任务数量、资产规范或视觉包装作为“产品进展”的主要指标。**

---

## 四、Blind Opening Test 当前被 UI 污染

本轮很重要的一个目标是：

> 一个不了解 Pi 的用户，能否在约 3 秒内自然看出“Pi 注意到了异常”。

但当前 intro CSS 直接显示：

> `Pi 正在看向风里的纸页`

这等于 UI 已经把测试答案告诉玩家。

于是即使用户说“Pi 在观察纸页”，我们也无法区分：

- 他是否真的读懂了角色动作；
- 还是只是读懂了屏幕文字。

### Round 3 要求

必须增加一个真正的 **Blind Opening Test 模式**：

- 隐藏“Pi 正在看向风里的纸页”；
- 最好同时隐藏“风把一段旧记忆吹散了”等解释型文字；
- 只给玩家 3 秒纯画面；
- 然后问：**“你觉得这个小角色正在干什么？”**

### 通过信号

玩家自然描述：

- “它发现了什么东西”；
- “它在看那些纸”；
- “它准备过去调查”；
- “它好像注意到了异常”。

### 失败信号

玩家首先描述：

- “这里有个红色圆环”；
- “这是一个喷泉”；
- “前面有个红门”；
- “不知道这个小人是干什么的”。

只有 Blind Test 通过，才能说镜头真的建立了 Pi 的主体性。

---

## 五、16 秒自动进入 Explore 不应保留

当前 `CityStoryHub` 中：

- 约 2.4 秒后自动进入 `invite`；
- 约 16 秒后自动进入 `explore`。

即使玩家没有点击“和 Pi 一起看看”，也会恢复完整城市 UI。

这在产品上破坏了刚刚建立的因果：

理想关系应该是：

`Pi 观察`
→ `Pi 表达意图`
→ `Pi 邀请玩家`
→ **玩家回应**
→ `共同开始行动`

当前逻辑实际上更像：

`播放 Opening Bumper`
→ `时间到了`
→ `恢复 Dashboard`

### Round 3 要求

保留：

`notice → invite`

可以由角色演出时间自动推进。

但：

> **`invite → action/explore` 必须由玩家显式行为触发。**

可以是：

- 点击“和 Pi 一起看看”；
- 明确 Skip；
- 或未来其他清晰输入。

玩家不响应时，Pi 可以继续轻量 idle、再次看异常、稍微调整 CTA，但不能因为 Timer 到点直接结束这段关系。

## 六、当前存在两套阶段系统，继续扩展会漂移

目前至少存在：

### 产品展示阶段

`intro / invite / explore`

主要由 `CityStoryHub` 本地状态和 Timer 驱动。

### 任务 / 场景阶段

`arrival / first-look / choose-question / plan / expedition / return / complete`

主要由任务事实和场景契约驱动。

此外还有 `memoryWindBeat = notice / hold / reframe`。

短期这三层可以靠人工映射跑通。

但如果复制到 12 个任务，极易变成：

- UI Stage 一套状态机；
- Mission State 一套状态机；
- Camera Beat 又一套状态机；
- 角色动画再加一套条件分支。

### 建议结构

后续应该明确：

#### 1. Domain State

负责：

- Pi 当前知道什么；
- Pi 当前正在做什么；
- 是否等待玩家；
- 哪些问题仍开放；
- 当前携带什么发现；
- 是否已重新判断。

#### 2. Presentation Beat

只能由 Domain State 派生：

例如：

`first-look`
→ `notice`

`awaiting-player-question`
→ `invite`

`player-committed`
→ `departure`

`returned-with-new-evidence`
→ `reframe`

Presentation 不应该自己用独立 Timer 决定剧情已经走到哪里。

---

## 七、不要继续过度优化“提包”本身

提包是一个有效隐喻：

> Pi 能把发现带回来。

本轮让 Pi 转身以后提包仍保持在镜头可见侧，是正确的镜头细节。

但必须防止团队把这个隐喻逐渐做成新的局部最优：

- 包再大一点；
- 锁扣再亮一点；
- 换肩动作再自然一点；
- 每章给包换一个道具；
- 包里增加更多视觉槽位。

Pi City 真正独特的不是：

> **Pi 有一个包。**

而是：

> **Pi 带回新的东西以后，原来的判断发生了变化。**

所以正式角色动画预算如果有限，优先级应当是：

`return`
→ `take-note`
→ `put evidence together`
→ `rethink`
→ `change direction`

而不是继续深度精修 Opening 中的 shoulder bag。

## 八、Round 3 只批准四项 P0

### P0-1：真正的 Blind Opening Test

目标：证明没有解释文字时，玩家仍然先读到 Pi 的意图。

执行：

- 5–8 名非技术玩家；
- 3 秒纯画面；
- 不解释 Pi、不展示答案型字幕；
- 固定追问：“你觉得这个小角色正在干什么？”

若多数玩家首先描述异常装置或环境，而不是 Pi 的观察行为，则继续修改镜头，不做全章推广。

### P0-2：取消 16 秒自动 Explore

目标：让玩家回应成为故事状态的一部分。

要求：

- `notice → invite` 可自动；
- `invite → next state` 必须由玩家行为或明确 skip 触发；
- 不得通过 Timer 自动回到 Dashboard。

### P0-3：把同级别精力投入 Return / Re-think

下一轮不要继续只 polishing Opening。

必须完成至少一次完整可见因果：

`Pi 带回发现`
→ `发现被放在一起`
→ `Pi 明显重新判断`
→ `新的方向 / 行动在世界中出现`

并测试玩家能否自然回答：

> “Pi 为什么后来换了一个办法？”

目标回答应引用“新带回来的东西”，而不是“那个地方后来亮了”。

### P0-4：收拢状态模型

在复制到其他任务前，明确 Domain State 与 Presentation Beat 的派生关系。

不得让 `intro/invite/explore` 成长为与 Mission State 平行的第二套剧情系统。

---

## 九、本轮不批准的扩张

在以上四项没有通过之前，不建议继续投入：

- 12 个任务的逐一 Opening Cinematic；
- 全章节 Pi 动画模板复制；
- 全城市正式资产替换；
- 继续扩展信任图与发现册功能；
- 为每章建立独立的 UI Stage 状态；
- 深度 Story → Trace 集成；
- 进一步包装资产生产文档作为主要进展。

这些工作可能最终都需要，但当前它们不能回答最危险的产品问题。

---

## 十、Round 3 最终裁决

### 如果问题是：第二章正式视觉是否已经完成？

**没有。**

当前 Pi、建筑、材质仍主要是程序化代理与低材质资产，无法代表最终美术质量。

### 如果问题是：是否找到了更正确的演出方向？

**是。**

特别是：

> 世界先出现 → Pi 先表达意图 → UI 后置 → 玩家回应后再共同开始。

这条线值得继续。

### 如果问题是：现在能否复制到 12 个任务并全面生产？

**不能。**

当前只证明了 Visual Agency Layer 正在变好。

真正决定 Pi City 是否成立的两个核心层仍然等待真人证据：

1. **Gameplay Causality**：玩家判断、新发现和 Pi 下一步之间是否真的形成可理解的因果。
2. **Story ↔ Trace Causality**：城市故事中的因果能否在真实 Pi 运行中再次被识别，而不是成为另一套教学动画。

因此 `0c4ad7e` 之后最应该回答的问题不是：

> “怎么把这一套做得更精致？”

而是：

> **“把解释文字拿掉以后，一个完全不了解项目的人，真的会觉得这是 Pi 发现了问题、正在邀请我一起弄清楚吗？”**

以及：

> **“当 Pi 带回新发现以后，玩家真的能看懂它为什么改变下一步吗？”**

只有这两个问题开始得到真人证据，Pi City 才有理由继续扩大生产。
