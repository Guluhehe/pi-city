# 第一章多委托初步实施记录

**状态：** 已实施并通过自动化质量检查。  
**目的：** 将初版策划中的三个动态居民委托，从“喷泉单任务示意”推进为同一座港口中可连续进入、会留下城市记忆的第一章。

## 已实现的体验链

玩家从 **心愿码头** 进入，而不是先面对旧式功能入口。码头把第一章组织为三件居民心愿：灯塔、邮包、喷泉。每完成一件，城市信任图会点亮一处，下一件心愿才自然来到码头；未实现的后续心愿只作为诚实的城市前瞻，不伪装成可点击关卡。[1]

| 委托 | 已实现的 Pi 现象 | 温和绕路与可选物 | 实时城市变化 |
| --- | --- | --- | --- |
| **灯塔还亮着吗？** | 修过也要在真正需要的傍晚确认。 | 提前回信带回“尚未确认”印章；图书馆可带回露露的童年小画。 | 灯塔地标从微亮到确认后的旋转强光，入口出现小画。 |
| **迷路的邮包** | 旧地址与新门牌共同改变投递判断。 | 提前投递带回只对上一半的回执；旧路牌可回看。 | 邮局红门、旧/新街牌和发光信封依据信息与送达状态变化。 |
| **只会唱半首歌的喷泉** | 工具结果与旋律页回到思考空间，改变 Pi 的下一步。 | 风铃绕路留下小铃片；完整旋律纸页可回看。 | 思考桌连接两项发现、同步阀、喷泉、乐手和感谢纸船逐步变化。 |

## 共同任务契约

灯塔和邮包使用新的纯 `city-missions` 状态机；喷泉保留已经验证的独立 reducer。三者都在 tutorial 侧运行，状态携带 `source: 'tutorial'`，不读写 `SemanticTrace`。任务中采用同一套可见节奏：**居民心愿 → Pi 初看 → 玩家基于观察提出还没弄清的事 → Pi 计划、出发、带回物件 → 物件改变新的选择或确认需求 → 回信与城市回应**。[2]

心愿码头的发现册与城市信任图由独立 `city-campaign` 状态管理。它只记录作者定义故事内的完成、发现与当前委托，不能被误作真实 Agent 记忆。

## 视觉与交互验收

真实本地 3D 捕获脚本 `scripts/capture_city_chapter_demo.mjs` 已以玩家的实际按钮路径得到以下画面：心愿码头、灯塔抵达、开放问题和 Pi 计划。验收截图确认第一眼为实时港口和居民心愿；灯塔开放问题以“城市里可观察的理由 + 去某处看看”呈现，不是追逐发光热点。截图审查后修复了选择面板的子元素定位冲突，并重新捕获验证文本层级清晰可读。

## 档案馆与诚实边界

新增的 **Pi 档案馆** 不会宣称城市故事就是某段真实运行。它清楚分开 Story、Concept 与 Evidence Run：用户可以停在故事里，也可以选择进入既有证据保存探索器；当前没有声明与三件心愿逐项对应的真实 Trace，因此档案馆保留诚实的距离。[3]

## 尚未伪装完成的初版内容

本轮交付第一章三项完整可玩委托，以及第二章到第四章的心愿前瞻。尚未实现的内容包括其余九项可玩委托、双心愿同时在手、跨居民等待反馈、星光节整合任务和持久化存档。它们应在非技术用户试玩三个第一章委托后，沿同一 Campaign / Mission 数据契约继续扩展，而不再复制新页面。
