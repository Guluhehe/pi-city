# Pi City 游戏化设计外部评审（GPT）

> **评审日期：** 2026-08-18  
> **评审对象：** `docs/research/2026-08-18-pi-city-game-design/` 下的 README 与 01–07 设计研究文档  
> **性质：** 独立产品评审，不代表既定产品承诺，也不替代真实玩家测试。

## 一、结论先行

这轮设计不是简单给 Pi City 增加“游戏化包装”，而是实质性重新定义了产品第一层入口：

**从“Agent 运行可视化 / Trace Explorer”转向“普通用户先通过城市任务体验 Agent 行为，再自愿下潜真实 Trace”。**

这是一个重要进步。

过去 Pi City 最难回答的问题之一是：**用户进入这个城市之后，究竟要做什么？**

当前方案给出了一个更清楚的回答：居民提出一个具体愿望，玩家陪 Pi 去观察、行动、带回新结果、重新判断、确认并回信。玩家不需要先理解 Request、Context、Tool Result、Verify 等技术词，而是在故事中先体验这些行为。

其中最值得保留的设计北极星是：

> 玩家离开时不一定会说出 Context 或 Tool Result，但应该能自然地说出：Pi 会先去看看；做完以后还会把新发现带回来想一想；确认真的好了才会告诉你。

这比“把 Agent 架构画得更漂亮”更接近一个真正的产品入口。

但当前仍处于**核心玩法假设尚未验证**的阶段。现在最不应该做的，是继续扩写 12 个任务、增加更多系统或投入完整 3D 美术。下一步应严格收缩为三任务 Greybox，验证“指下一站 → 带回发现 → Pi 再想 → 世界变化”本身是否成立。

---

## 二、这轮设计真正解决了什么

### 1. Pi City 的第一层产品终于有了明确角色

新的产品结构已经开始从：

`Agent 结构 → 可视化 → 用户观看`

转向：

`居民问题 → Pi 办事 → 玩家判断 → 新发现改变 Pi → 城市留下变化 → 好奇者进入真实 Trace`

这使 Pi City 不再要求用户先对 Agent 架构感兴趣。

用户可以先关心一个更自然的问题：

**“Pi 能不能把这件小事办好？”**

这是正确的入口变化。

### 2. “信息”开始从抽象状态变成城市中的实体

将不同类型的信息映射为可携带物件，是这轮方案里最有效的视觉与交互决策之一：

- Request → 心愿信封
- Memory → 相册页
- Observation → 观察卡
- Tool Result → 工具回执
- Verify → 萤火印章
- Answer → 感谢纸船

这个设计的价值不只是可爱，而是让原本不可见的 Agent 信息流变得可以被玩家看到、携带、带回和重新组合。

尤其是“结果回到思考塔后，改变下一步”这一演出，应当成为整个产品最重要的可见因果。

### 3. 方案已经意识到：不能把游戏做成“跟着高亮跑”

这是非常关键的修正。

如果核心玩法最后只是：

`某地点亮起 → 玩家点击 → Pi 跑过去 → 下一个地点亮起`

那么它不是游戏，只是交互式流程动画。

v0.3 中提出的规则值得直接保留：

> 如果玩家无法在选择前说出一句“我选这个，因为……”，这个选择就不应进入任务。

每局只需要一个真正的判断点，不需要制造很多复杂分支。

例如：

- 先查旧地址，还是先看现在的新门牌；
- 修好之后直接回信，还是先去确认；
- 两张心愿单先帮谁；
- 小包这一趟带哪两件发现物。

这些选择的意义不在于“答对”，而在于玩家能够解释自己的理由，并看到不同的世界后果。

### 4. “温和”不再等于“没有规则”

把失败改成“温和绕路”是合理方向，但更重要的是 v0.3 又补了一层：

**绕路必须产生可见因果和新信息。**

例如玩家过早回信，不能只是系统把玩家送回上一步；而应该让灯再次熄灭、居民看到问题、Pi 得到一个“尚未确认”的新事实，并自然产生下一步。

这使玩家感受到的是：

“我和 Pi 新知道了一件事。”

而不是：

“游戏判我点错了。”

这是符合 Pi City 气质的规则设计。

### 5. 公开玩家研究确实帮助设计砍掉了一些错误方向

999 条 Steam 评论和 Reddit 交叉验证不能替代 Pi City 自己的用户研究，但它们有效完成了一件事：

**对设计假设施压，并帮助排除一些看似‘更游戏化’、实际上会稀释核心体验的方案。**

当前明确拒绝迷宫、战斗、潜行、倒计时、排行榜、货币、抽卡、大量收集、强制技术课程等方向，是合理的。

这些研究最有价值的结论不是“cozy game 很受欢迎”，而是：

- cozy 不等于没有玩法；
- 短不等于浅；
- 无失败不等于无规则；
- 玩家愿意自己发现复杂规律；
- 当核心循环不成立时，增加另一套玩法只会掩盖问题。

## 三、当前最需要警惕的四个风险

### 风险 1：核心玩法仍未被证明

现在几乎所有内容最终都建立在一个核心动作上：

**“帮 Pi 指下一站。”**

这是目前最大的产品假设。

文档已经通过判断点、可选发现、城市变化、温和绕路、居民反馈等方式努力增强它，但仍不能从纸面证明：

**给 Pi 选择下一站这件事，本身是否足够有趣。**

因此，三任务 Greybox 不是“开发第一阶段”，而是一个真正的产品决策门。

如果三个任务玩下来仍然只是“看提示 → 点地点 → 看动画”，那么后面的十二任务、城市信任、发现册、小包容量等系统都没有继续扩展的价值。

### 风险 2：最危险的失败不是“不好玩”，而是“把 Pi 教错”

当前城市映射中存在一个必须持续防范的问题：

`旧日图书馆 → Memory`

`观察台 → Observation`

`工具坊 → Tool`

`暮色花园 → Verify`

这些映射很好理解，但非常容易让普通玩家最终形成一个错误心智模型：

> Agent 就是按照固定 SOP 依次经过几栋楼。

而 Pi 真正重要的机制并不是固定流程，而是一个动态循环：

**模型基于当前可见 Context 做判断 → 调用工具 → Tool Result 回到 Context → 模型基于新增信息重新判断下一步。**

同一地点可以被多次访问，顺序也不固定；有的任务甚至不需要经过某些地点。

因此后续设计应坚持：

> **城市表达的是 Agent 的循环机制，而不是 Agent 的固定工作流。**

“思考塔 + 结果回流 + 下一步变化”应该比“六个地点的标准路线”更重要。

### 风险 3：Game 与 Evidence Explorer 可能逐渐裂成两个产品

目前方案提出：

**前台是城市任务，后台档案馆是真实 Trace。**

这是比原先更自然的结构，但它还没有真正证明二者为什么必须属于同一个产品。

如果未来只是：

`玩一个虚构故事 → 想学技术的人打开一个 Trace Viewer`

那么 Pi City 很容易最终变成：

**一个 cozy game + 一个开发者 Trace 工具。**

两个产品都可能不错，但彼此不真正需要。

更值得追求的状态应该是：

**Story 是第一世界，Trace 是第二世界。**

玩家先在故事中形成一个直觉，之后进入 Trace 时，能突然认出：

“原来刚才我看到的‘Pi 把东西带回来重新想’，在真实运行里就是这段 Tool Result 进入 Context 后导致下一次动作发生变化。”

如果真实 Trace 能反过来让故事体验变得更有意义，二者才真正形成闭环。

### 风险 4：999 条相邻游戏评论不能证明 Pi City 用户需要这个产品

这批评论适合回答：

- 什么会让轻量游戏变空洞；
- 什么会破坏低压力体验；
- 什么样的规则容易让玩家产生自主发现感。

但它们不能回答：

**“一个对 AI/Agent 有一点好奇、但不懂技术的人，是否真的愿意玩 Pi City？”**

因此这轮研究应被理解为“设计压力测试”，而不是需求验证。

真正决定方向的证据应该来自 Pi City 自己的灰盒试玩。

## 四、对三任务 Greybox 的补充建议

当前 Greybox 方案总体正确。我建议把测试进一步聚焦到四个问题，并把其他指标都视为次级信号。

### P0-1：玩家是否真的看懂“结果回流会改变 Pi”

这是整个 Pi City 最重要的产品命题。

玩家完成喷泉任务后，不应该只说：

“我拿到了一个新道具，所以下一站亮了。”

更理想的自然语言应该接近：

“Pi 拿到了新的东西，回来重新想了一下，所以知道下一步该去哪了。”

如果这个理解不成立，应暂停其他学习内容和系统扩展，优先重做结果回流演出。

### P0-2：玩家是否能解释一次真实选择

每局至少记录一次：

> “你为什么选择这里？”

不是为了判断玩家对错，而是验证选择是否真的具有意义。

如果大多数回答是：

- “因为它亮了”；
- “感觉游戏让我点这里”；
- “其他地方不能点”；

说明目前仍然是隐藏教程，不是玩家判断。

### P0-3：玩家是否把 Pi 当作一个行动中的角色，而不是鼠标光标

观察玩家是否自然使用：

- “让 Pi 去看看”；
- “Pi 还不知道”；
- “Pi 拿回来这个以后……”；
- “我想让 Pi 先确认一下”。

如果玩家始终说：

- “我点这里”；
- “游戏让我去这里”；
- “这个按钮解锁了”；

说明 Pi 作为城市助手的角色感还没有成立。

### P0-4：完成任务后，玩家是否仍然想看这座城市

这是判断“Agent 教学 Demo”与“真正世界体验”之间差异的重要信号。

玩家是否会：

- 看一眼灯塔后来变成什么样；
- 去找可选发现；
- 注意居民变化；
- 问下一个人发生了什么；
- 想再走一次另一条路线。

如果玩家理解 Pi，却任务结束就立即关闭，那么教学层可能成立，但 Game 层仍未成立。

## 五、建议暂缓的内容

在三任务 Greybox 通过之前，建议继续冻结以下工作：

- 完整 12 任务生产；
- 大规模正式 3D 资产；
- 完整角色动画；
- Pi 小包的复杂策略扩展；
- 发现册和大规模收集；
- 城市等级 / 信任数值系统；
- 动态 LLM 任务生成；
- 真实仓库写入；
- 开放世界移动；
- 复杂自由相机；
- 大量 Trace 深度集成。

这些内容不能证明核心循环成立，过早制作反而会提高沉没成本。

## 六、下一阶段建议：把 MVP-0 定义得更硬

建议下一步只实现三个任务：

1. 灯塔还亮着吗？
2. 迷路的邮包
3. 只会唱半首歌的喷泉

三个任务共同只需要验证一个核心心跳：

`居民请求`
→ `Pi 思考`
→ `玩家做一次有理由的选择`
→ `Pi 去观察 / 行动`
→ `带回新发现`
→ `新发现进入思考塔`
→ `Pi 的下一步发生变化`
→ `确认`
→ `居民与城市留下变化`

如果这个循环能够让非技术玩家自然产生：

> “哦，原来 Pi 拿回来这个东西以后，刚才那个判断就变了。”

那么 Pi City 才真正跨过了：

**Agent Visualization → Agent Game**

这条线。

如果没有跨过，不应通过“增加更多系统”来救它，而应重新设计核心动词。

---

## 七、建议下一轮设计重点

如果三任务 Greybox 方向继续推进，下一轮文档不建议继续扩充任务数量，而建议优先回答三个更深的问题：

### 1. 如何让城市表达“循环”而不是“固定流程”？

重点研究：同一个地点重复访问、顺序变化、跳过某些地点、新 Tool Result 改变原判断等情况如何在视觉上自然成立。

### 2. Story 与真实 Trace 如何形成真正的双向映射？

不是简单在结尾放一个“查看后台”的按钮，而是设计一种体验，让玩家进入 Trace 后能认出自己刚刚在城市中体验过的因果。

### 3. 核心动词是否最终仍然应该是“指下一站”？

Greybox 的任务不是证明现有方案正确，而是允许推翻它。

如果真实玩家理解 Pi，但觉得选择下一站缺乏参与感，应优先重新设计核心动词，而不是继续增加小玩法。

---

## 八、给下一位评审者 / AI 的挑战问题

1. 这个产品最核心的乐趣到底来自“帮居民”，还是来自“看 Pi 根据新信息改变判断”？两者冲突时应该保哪一个？
2. 玩家是否真的需要替 Pi 选择下一站？如果 Pi 自己走，玩家只负责观察、携带或确认，会不会反而更符合 Agent 本质？
3. 两格小包是在帮助玩家理解 Context 选择，还是过度把 Context 简化成“容量限制”？
4. 如何避免六个地点最终变成六种固定 Agent Step？
5. Story Mission 与真实 Trace 之间，能否建立一一对应或局部对应的“翻面”体验？
6. 如果完全移除 Pi 技术学习目标，这三个任务本身还值得玩吗？如果答案是否定的，Game 层可能还不够独立。
7. 如果完全移除 cozy 城市包装，Agent 的“新结果回流 → 重新判断”本身是否仍然有可玩的结构？这决定了核心设计是否真正来自 Pi，而不是来自题材。

## 最终判断

这轮设计值得继续，但**值得继续的是核心假设验证，不是内容扩张。**

它已经帮助 Pi City 找到了一个比“Agent 架构可视化”更有潜力的入口：

**让人先陪 Pi 把一件事办好，再理解 Pi 为什么能把事情办好。**

下一步成败不取决于文档还能写得多完整，而取决于三个 Greybox 任务是否真的让普通玩家在没有术语解释的情况下，看见并享受：

**观察 → 行动 → 新结果回流 → 重新判断 → 确认。**
