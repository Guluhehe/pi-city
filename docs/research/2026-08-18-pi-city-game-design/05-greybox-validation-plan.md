# Pi City 三任务灰盒：可玩性与 Pi 学习验证方案

## 验证目的

三任务灰盒的目的不是证明玩家能“完成教程”，而是验证三个更严格的问题：普通玩家会不会自发把 Pi 当作一个值得帮助的城市角色；他们会不会看懂新发现如何让 Pi 改变下一步；以及他们是否愿意为了城市、角色和可选发现继续玩，而不是只把它当成一次漂亮演示。

在这三个问题没有通过前，不应进入完整角色建模、大量正式美术、十二任务生产、真实 Trace 深度整合或复杂成长系统。

## 试玩版本范围

| 内容 | 必须包含 | 明确排除 |
|---|---|---|
| 任务 | 灯塔、迷路的邮包、半首歌喷泉。 | 第四任务以后、小包两格、双委托。 |
| 地图 | 思考塔与六个固定地点；Pi 路线；三项街区变化。 | 自由移动、开放世界、镜头控制器。 |
| 互动 | 选择下一站、查看发现物、一次可选发现、一次温和绕路。 | 自由输入、拖拽背包、复杂菜单。 |
| 叙事 | 居民一句请求、Pi 短对白、结束时可跳过复盘卡。 | 长对话树、配音、大量背景故事。 |
| 视觉 | 可读的色块、轮廓、物件与最低限度动画。 | 正式材质、复杂特效、高保真角色表演。 |
| 音频 | 八类占位状态声与基础环境底层。 | 正式配乐、完整音效库。 |

## 受试者画像与数量

首轮寻找 5–8 位不以软件开发为职业、平常会玩轻量手机／网页／主机游戏的人。至少包含 2 位对 AI 有好奇但不熟悉 Agent 术语的人，以及 2 位对 AI 兴趣一般的人。熟悉 Pi、LLM 开发或当前 Pi City 代码的人可以在第二轮补测，但不应成为首轮主要样本，因为他们会自然补全产品希望教给大众的东西。

每次测试约 25–35 分钟：3–5 分钟背景访谈，12–15 分钟独立游玩三局，8–12 分钟回顾与追问。主持人在游玩阶段不解释地点含义、不提示正确路线、不主动说明 Pi 概念；只在玩家卡住超过 20 秒时记录并给予最低限度的可用性协助。

## 试玩流程

### 阶段 A：无说明首次进入

向玩家只说：“这是 Pi City。这里有一位叫 Pi 的小助手，会帮居民办事。请按你觉得自然的方式玩。” 不说 Pi 是 Agent，不解释工具、记忆或验证。观察他们是否自然识别心愿单、Pi、思考塔与可去地点。

### 阶段 B：连续三局

让玩家自然完成灯塔、邮包与喷泉。主持人记录每一次选择、停顿、误点、重读对白、是否查看可选发现、是否在温和绕路后理解新方向、完成后是否观察街区变化。只在任务间询问：“接下来你觉得 Pi 会怎么做？”不问技术名词。

### 阶段 C：从故事语言走向 Pi 语言

玩家完成第三局后，先问三个无术语问题，再展示一次可跳过的“Pi 原来是这样想的”卡。随后询问玩家是否愿意点进“后台档案馆”，并让他们自己说明这扇门可能有什么。

| 问题 | 想验证的理解 | 不应接受的表面答案 |
|---|---|---|
| “为什么 Pi 修好灯后没有马上给露露回信？” | 需要确认结果，行动不等于完成。 | “因为游戏规定要去花园。” |
| “喷泉拿回新节拍后，为什么还要回思考塔？” | 工具／行动的新结果会影响下一步。 | “因为地图只有那条路。” |
| “旧地址和新门牌同时出现时，Pi 在做什么？” | 旧信息与当前观察共同帮助判断。 | “在收集道具。” |
| “后台档案馆可能是什么？” | 对 Pi 的真实运行产生健康好奇。 | “不知道，可能是设置。” |

## 建议的通过门槛

下表阈值是决定是否进入下一制作阶段的内部假设，并非对用户体验的统计结论。样本很小，必须同时看录像、访谈原话和实际行为；任何严重的理解误区都比单一完成率更重要。

| 验证项 | 通过信号 | 暂定门槛 | 若未通过，先改什么 |
|---|---|---:|---|
| 首次可用性 | 玩家在 20 秒内做出第一个合理地点选择。 | 5/6 以上。 | 地点高光、Pi 对白、入口镜头。 |
| Pi 角色代入 | 玩家以“帮 Pi”“让 Pi 去看看”的语言描述操作。 | 5/6 以上。 | Pi 动作、居民目标、对话关系。 |
| 结果回流理解 | 玩家能说“新发现带回来后 Pi 会再想”。 | 4/6 以上。 | 发现物动画、塔内关联、回流音效。 |
| 验证理解 | 玩家能区分“修过”与“确认真的修好”。 | 4/6 以上。 | 灯塔／花园演出、居民反馈、复盘句。 |
| 温和绕路感受 | 绕路后继续尝试，不询问是否失败。 | 5/6 以上。 | 绕路时长、Pi 语气、下一步指向。 |
| 自发探索 | 玩家主动查看至少一个可选发现或完成后街区变化。 | 3/6 以上。 | 可选物可见性、城市变化、角色诱因。 |
| 继续游玩意愿 | 自发问下一位居民／下一处变化，或愿意再玩一次不同路线。 | 4/6 以上。 | 章节钩子、任务差异、收藏反馈。 |
| 后台好奇 | 自愿点击或表示想进入档案馆。 | 2/6 以上。 | 复盘卡用词、档案入口承诺。 |

“后台好奇”的门槛故意最低。Pi City 的入口首先是完整游戏体验，不应将玩家是否愿意学习术语当作成败。只要玩家能在故事语言中正确理解 Pi 的行为，产品就已达成最重要的学习目标。

## 最小行为埋点

原型只需记录可解释事件，不收集文本输入或个人信息。事件数据用于发现哪里让人困惑，不能用来给玩家打分。

| 事件 | 字段 | 要回答的问题 |
|---|---|---|
| `mission_started` | missionId、entryMode。 | 从哪里进入任务。 |
| `location_offered` | missionId、locationIds。 | 玩家看见了哪些选择。 |
| `location_chosen` | missionId、locationId、choiceIndex、secondsSinceOffer。 | 选择是否迟疑，路线如何发生。 |
| `gentle_detour_seen` | missionId、detourId。 | 哪类绕路出现。 |
| `optional_discovery_opened` | missionId、discoveryId。 | 可选内容是否有吸引力。 |
| `result_returned` | missionId、artifactType。 | 结果回流是否发生。 |
| `mission_completed` | missionId、durationSeconds、routeId。 | 节奏与不同路线。 |
| `reflection_opened` | missionId、conceptId。 | 玩家是否愿看解释。 |
| `archive_intent` | missionId、opened。 | 后台档案的好奇度。 |

## 迭代决策树

| 观察到的问题 | 不应做的反应 | 正确的首选修改 |
|---|---|---|
| 玩家只是在找发亮按钮，不知为何要去。 | 增加教程文本。 | 重写居民愿望与 Pi 的短句，强化地点动作名。 |
| 玩家看见发现物，但不知道它改变了什么。 | 增加日志面板。 | 把发现物带回塔内的物理关联做得更明显。 |
| 玩家认为绕路是惩罚或失败。 | 删除所有选择。 | 缩短绕路、让角色说清世界原因、立刻给可用新线索。 |
| 所有人直线通关，不看城市。 | 强制要求可选收集。 | 给可选发现加角色关系、街区变化或轻微路线诱因。 |
| 玩家觉得可爱但没学到 Pi。 | 在开场解释 Agent。 | 在第二任务里重复同一原则的不同情境，并改进复盘卡。 |
| 玩家懂 Pi 但不想继续玩。 | 增加更多术语或技术深度。 | 增加任务之间的角色关系、城市公共目标和可变路线。 |

## 原型完成后的三种决策

| 结果 | 含义 | 下一步 |
|---|---|---|
| 通过核心理解与继续游玩 | 玩法心跳成立。 | 进入正式视觉垂直切片：完成 Pi、六地点、三任务的高保真版本。 |
| 理解通过、意愿不足 | 教学有效但游戏不够有吸引力。 | 迭代角色目标、可选发现、城市变化与任务变化，不急于加系统。 |
| 意愿通过、理解不足 | 城市很有魅力，但 Pi 逻辑尚未被体验到。 | 强化结果回流、确认与复盘；保留故事魅力。 |
| 两者都未通过 | 当前入口的核心交互不成立。 | 回到第一局，重做“指下一站—带回发现—再选择”的反馈闭环。 |
