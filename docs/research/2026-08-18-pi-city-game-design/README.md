# Pi City 游戏化学习设计评审包

> **状态：** 设计研究与可验证原型提案；未实现，不应被视为产品既定承诺。

本目录将 Pi City 从“可播放的 Agent 运行可视化”扩展为“面向非技术用户的轻量城市任务体验”的策划过程集中在一起，供产品、游戏设计、UX、美术、工程与其他 AI 进行独立评审。

Pi City 当前产品的核心承诺仍是 **evidence-honest**：导入的 Pi Trace 必须保留 Observed / Derived / Synthetic 边界，视觉层不得捏造运行行为。这个提案不改变该承诺。它增加的是一层作者定义、明确标识的“城市故事”入口：玩家陪小助手 Pi 帮居民办事，在轻量任务中直觉理解请求、记忆、观察、工具行动、结果回流、验证与回答；好奇者再自行进入现有 Evidence Explorer 和真实 Trace。[1]

## 本提案的核心判断

| 判断 | 具体含义 |
|---|---|
| 玩家不是工程师 | 不要求代码、JSONL、工具参数、token 或运行调度知识。 |
| Pi 不是聊天框 | 通过城市路线让玩家体验 Pi 如何把请求变成观察、行动、新结果与回应。 |
| “指下一站”必须有判断 | 不能沦为追随高亮的跑腿；每局至少一个选择要改变玩家这次看到的因果或城市反应。 |
| 温和不等于无规则 | 不做分数与硬失败，但每条绕路都应有可见原因、新发现和清楚下一步。 |
| 学习先于术语 | 玩家先在不同故事中体验规律，再自愿查看 Pi 小知识或真实档案。 |
| 技术真实性不妥协 | 教学场景与导入 Trace 在数据与 UI 上永久分层；教学模拟不写回真实 Trace。 |

## 有意未做的内容

本包**不**建议在验证前加入自由跑图、迷宫、战斗、潜行、倒计时、排行榜、货币、抽卡、长教程、强制技术课程、动态 LLM 出题、真实仓库写入或开放式任务生成。它们无法证明“观察—行动—结果回流—再想”是否本身具有乐趣，反而可能掩盖问题。

同样，本目录不包括公开玩家评论的原始文本或账号资料。用户声音研究保留了方法、聚合主题、匿名化摘录和来源链接；原始抽样数据仅用于本地研究，以保护公开评论者的隐私并保持仓库整洁。

## 建议其他 AI 的评审问题

请不要只评价文档是否写得完整。请优先挑战下列可证伪问题：

1. **核心循环是否真的有游戏性？** 玩家是否能在不懂 Pi 的前提下，说出某次路线选择的理由并期待结果不同？
2. **隐性学习是否可信？** “工具结果回到思考塔、再影响下一步”的城市演出是否足够让玩家形成正确而不过度简化的 Pi 心智模型？
3. **首局是否过于线性？** 灯塔任务中的温和绕路、可选发现与确认步骤，是否会被看成隐藏教程而非玩家行动？
4. **内容生产是否可控？** 12 个小任务是否能以统一任务语法持续生产，而不依赖每局发明一套新系统？
5. **现有架构能否承载？** 教学故事、发现物和双层 UI 是否可以在现有 Semantic Trace、Experience、World 与 game reducer 边界中实现，而不污染真实证据模型？
6. **视觉方向是否延续 Pi City 的身份？** 工业港口与居民层的组合，是否既有温度又没有退化为通用 cozy game？
7. **玩家声音是否被正确使用？** 公开评论样本是否支持这些优先级，还是存在过度外推、选择偏差或需要用户研究补证的地方？

## 评审后的首个决策门

若评审认为方向成立，下一步应是 **MVP-0 三任务灰盒**：只实现灯塔、邮包、喷泉；思考塔、六个地点、Pi 路线、发现物回流、可选发现、温和绕路和最小复盘。先招募 5–8 位非技术玩家进行观察，再决定是否进入正式美术垂直切片。

若评审认为方向不成立，必须指出该先推翻哪一项可验证假设：玩家身份、路线选择、学习映射、故事任务语法或现有架构兼容性。不要建议通过“再加更多系统”来回避核心问题。
